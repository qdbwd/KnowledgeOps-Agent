# 开发问题与解决记录

更新：2026-10-16。实现进度见 [progress](progress.md)，范围见 [实施计划](implementation-plan.md)。不记录密钥。下方旧交付限制保留其历史语境，当前状态以progress为准。

## DEV-099：清理边界遗漏子图引用、作业交接及资产编辑锁序

主图状态没有链接，不代表整个执行已不需要材料：工具子图和待合并结果可能仍在引用它。真实保存器验证复现了旧逻辑会把这样的材料标记为过期。现在用公开分页接口检查各namespace的最新状态及pending_writes，历史作用域也按稳定拥有者寻找，不依赖批次记录还存在。每日复查重新读取检查点，释放已经失效的旧保留引用。

另外两项并发验证复现了应用层的交接问题。已完成的子清理作业若先被TTL清掉，失败中的父作业就失去继续清理所需的进度；现在父作业消费前继续保护。偏好/角色编辑先取得业务行锁、清理先取得控制锁，可能形成相互等待；现在统一写入入口锁序。定向检查使用真实PG连接、文件和保存器，不依赖模型输出，失败证据与修正后的通过证据均保留；最终整体验收另行核对。

## DEV-098：首次初始化检查点保存器被清理事务反向等待

会话删除的页面已经显示“清理中”，后台却长时间不能完成。数据库等待信息表明，清理事务尚未提交，保存器setup创建并发索引又在等待这个旧事务结束；程序在同一条调用链中等双方完成，构成应用层自等待。此前组件使用提前初始化的实际保存器，未覆盖首次打开保存器的工厂路径。

现在详情删除和材料回收先在业务事务之外初始化保存器，再开启持锁事务复查对象并执行公开删除/读取接口。不修改LangGraph表，不把增加超时作为修复。隔离浏览器验收从全新schema启动，删除及未完成任务保护通过，桌面与窄屏页面已查看；原失败证据保留。该问题说明真实组件可用不等于它们在实际事务组合中一定可用。

## DEV-097：快速取消没有结束时间，会让已停止任务一直无法进入保留期

生命周期检查不能仅凭状态写着cancelled就立即删除，因此需要实际结束时间。接入时发现，排队或等待任务被用户直接取消，部分路径只改状态，没有记录finished_at；这类任务虽然没有执行者，却会永久落在“无法证明结束时间”的保护条件中。学习推进回执也需要与直接取消同步，否则仍表现为待推进。

新取消操作现在在同一控制事务记录真实时间，运行中的任务仍由执行者在安全点收束后记录，不提前宣称外部操作结束。已有缺失时间的记录不回填猜测日期，继续列为保护项。学习推进及协作回执也纳入资格判断，根Run结束不代表可靠交接全部解决。定向隔离检查覆盖直接取消、旧数据保护及原异步/学习调度；证据见progress的lifecycle-settlement-regression。未消费子通知仍受保护，不把取消伪装为主Agent已经阅读结果。

## DEV-096：客户端保存了 MCP 续接状态，服务重启仍可能拒绝它

双轮补问第一次已经正确进入等待，但关闭 stdio 连接并重建后，服务拒绝原 requestState，调用不能继续。核对 MCP 2.3.0 的 request_state 边界与 FastMCP 4.0.11 服务配置后确认：服务默认使用进程级临时密钥封装状态；新进程的密钥不同，即使客户端完整保存 token，也不能让服务再次接受。不能通过客户端重发没有答案的首轮解决，否则会重复已有远端操作。

客户端继续使用官方 session 的后续轮参数，服务拒绝时给出有界说明并保留未知结果。需要跨进程恢复的测试服务用临时文件保留随机签名密钥；产品不替第三方服务生成或管理这个密钥，也不降低 SDK 校验。持久服务的双轮和跨 worker 恢复已验证，失效路径及浏览器继续验收。此前另一次失败来自测试关闭整个应用连接管理器后又复用已销毁实例；修正为关闭具体连接范围，真正的 worker 重启由独立进程覆盖，不能把测试生命周期错误当成生产恢复缺陷。

## DEV-095：独立子运行不能沿用同步调用的身份与结束判断

将子任务交给独立 worker 槽后，原来依赖父线程的一些隐含前提不再成立。等待审批的 interrupted 子任务曾被判为已经结束；角色撤回后主任务无法取回已保存的失败报告；明确恢复又无法在原委派位置重试失败任务。旧同步测试也假定 start_child 创建后立即开始执行，掩盖了调度边界。

当前按状态和等待原因共同判断是否收束，读取旧结果与重新执行分开校验。失败重试只接受当前代次的真人恢复事件，并由同一委派调用重新入场；自动通知不触发，历史失败不批量重跑。测试使用真实图中断、持久 Run 和生产执行入口继续，独立 worker 并发另有跨进程证据。MCP 调用的父 worker 身份假设也已修正：校验实际子执行者，同时保留根任务控制和角色权限检查；新守卫不放宽原来仅主任务可用的发布守卫。

最终兼容回归又发现审批服务仍只接续主Run：子图已经保存等待决定的检查点，主图处于waiting_children，旧入口却因主图不是interrupted而拒绝真人决定。现在决定校验审批实际所属的子Run，原outbox只在该子任务待办齐全后投递它；根任务暂停、取消、异常重启或尚未应用的真人引导仍阻止自动继续。重复决定不增加新代次，暂停期间只保存决定，明确继续后仍用原子图检查点。这里补的是恢复接入，不授予子角色命令权限。旧显式验收器也改为投递真实子Run，避免把主图等待误记成一次任务结束。

## DEV-094：等待子结果必须同时保持任务接续和真人介入

异步委派把子任务移交给持久调度后，原来的“运行已经停止”判断不再覆盖全部状态。主任务虽然释放执行线程，子任务仍在推进；如果沿用结束时关闭 SSE 的逻辑，网页会停留在旧状态。原消息插入接口只允许运行、暂停和等待用户，也会拒绝用户在等待子结果时提出新安排。

现在 waiting_children 保持事件订阅，结果通知在 PG 去重并由原 outbox 接续。用户明确插入的真人消息可提前唤醒原图，优先应用新要求；普通排队消息不会唤醒，也不把未完成的子结果伪装成完成。分页历史刷新与活跃等待状态分开读取，避免每次刷新都卸载订阅、重复重播等待事件。子任务管理的补充指令另有幂等请求身份和来源，网络重试不会重复追加，也不会扩大权限。

最终浏览器回归又复现一个切换窗口：后台已完成，页面仍显示等待。`running`和`waiting_children`分别查询，主任务由等待切到queued时两组查询可能都返回空；此时分页列表还保留旧waiting项，既没有活跃观察者，也不满足旧排队轮询条件。现在把已知的未终结Run作为观察者回退，直到拿到终态。组件替身改为真实遵守status筛选，再覆盖等待→排队→完成；不能靠放宽页面等待时间掩盖丢订阅。

独立 worker 验证用真实 Celery 三槽、Redis 和 PG 检查点，供应商替身通过同步屏障证明同时推进；重启仍等待真人恢复，随后沿用原主子任务及预算。定向图检查另证明新要求在响应途中到达会阻止旧工具提议，以及主任务等待时可以通过新指令取消子任务。剩余 MCP 人工待办、旧学习协作和最终跨模块收束检查继续保留在交付核对表，不由这些局部结果推断全部完成。

## DEV-093：保持客户端连接，不一定保留了服务端会话状态

补齐MCP连接池时，最初的健康检查使用`ping`，真实本地协议返回Method not found。改用无副作用的工具目录读取后，客户端连接已经保持，但计数工具仍每次返回1。进一步用同一官方客户端分别运行自动协商与握手模式，发现自动协商得到2026-07-28逐请求协议；服务端每次请求获得新的状态身份，而握手模式连续调用返回1、2并保持同一会话。这是协议语义差异，不能通过忽略异常或只检查池里对象相同来修正。

核对FastMCP官方协议文档和锁定源码后，保留自动协商默认值，提供连接级`protocol_mode: legacy`，直接调用SDK受支持的模式。新协议照常使用，依赖持久会话的服务可以显式选择握手模式；工具结果报告实际协议、连接是否复用，MCP页面说明这一边界。新旧协议都用工具目录读取验证连接，业务调用仍核对Schema和许可。stdio/HTTP状态、断线、超时、撤回及图恢复分别验证，原始失败证据保留在artifacts/verification/mcp-session-protocol.xml和mcp-session-protocol-fixed.xml；最终结果见progress，不把早期失败覆盖成已通过。

## DEV-092：目录迁移后，源码可运行但安装包可能漏文件

按功能整理目录时，源码树中的 `app/runs` 和 `features/runs` 都存在，开发环境及浏览器也能读取；但独立导入生成的 Python wheel 时，报缺少 `knowledgeops_agent.app.runs`。原因是原 `.gitignore` 的 `runs/` 匹配任意层级，原本用于忽略运行产物，现在也把同名功能源码排除。Hatch 构建遵循该忽略规则，因而构建成功不代表包内源码完整；前端新运行页面也会被 Git 忽略。

已将规则限定为根 `/runs/`，继续忽略运行产物，允许跟踪功能源码。重新构建后，在源码路径之外导入安装包，核对稳定 API/worker 入口及配置、Skills、提示、tokenizer 和上游资源。另将依赖 `__file__` 相邻位置的资源访问统一到 `core/resources.py`，避免源码移入子目录后读取错误。这个问题说明目录重组需要核对忽略规则和构建输入，不能只验证开发模式的导入。证据入口见progress。

## DEV-091：审批完成后的重启、取消与结果保存需要分别恢复

审批接入后，“等待执行”和“等待用户”不能只用同一个interrupted状态判断。命令已经批准、调度已入队但尚未执行时重启，原审批已处理，若页面仍按waiting_approval隐藏人工恢复按钮，用户就没有下一步入口。当前恢复检查按PG事实区分：尚有待办则显示确认，存在未提交命令结果则显示unknown，其余保留普通人工恢复。服务启动本身不自动执行任务。

取消同样要撤销未执行提议，否则既可能在恢复时继续旧批准，也可能被残留pending永久阻塞。取消保留历史决定并把原动作标为失效；显式恢复由图接到拒绝反馈，重新考虑。取消时尚有unknown命令，恢复只重开核对入口；用户明确skip/retry之后才继续，retry是新的单次许可和计费尝试，仍受实时deny/工具上限约束。

工具进程成功返回，也不等于结果已经持久保存。原始结果的脱敏、长结果外置或回执写入异常都处于副作用与持久结果之间，统一保留unknown，不能错误地把一次可能已写入文件的操作当成普通工具失败并自动重试。真实临时文件和真实Agent图注入故障验证这条边界；这不证明任意Shell可以做到严格只执行一次。

前端实际浏览器另发现快速连续修改执行模式和思考档位时，第二次提交可能沿用异步GET中的旧修订。已把PATCH成功返回的设置立即作为下一次操作的版本，多窗口冲突仍由后端拒绝。原生中断、PG重开、取消/恢复和浏览器证据集中在progress，不为常规格式修正另写问题条目。

## DEV-090：真实资料整理试用暴露内容边界与记录反馈问题

## DEV-089：复制完整技能包后，测试样例阻断了整个技能目录

用户复制DeerFlow技能后，skill-reviewer内部故意缺少description的测试样例被当作正式技能，导致load_skills整体报错。原因是入口发现与包内资源收集混用：先找到顶层技能，再递归收集Markdown，却继续把每个同名SKILL.md当作新入口。同时旧快照只包含Markdown，脚本和模板不能随运行版本使用。

参考DeerFlow 3343522的包边界测试与实现，将入口发现和资源收集分开。嵌套样例保留为资料，不能成为目录项或子角色选项；已启用包的脚本和附属资源纳入固定快照，通过现有execute取得一次调用的临时资源目录。暂不兼容的包保留但不暴露给模型，管理页面说明原因。顺带修正资源可用性检查仍使用默认SKILLS_PATH的问题，使SKILLS_DIRECTORY自定义目录与冻结、恢复、撤回使用同一来源。

离线文件/真实子进程检查与Agent图联调覆盖旧版本执行、二进制模板、子角色目录、路径越界、禁用和撤回；实际复制目录可正常发现。原失败已复现，不归因于模型或Docker。GitHub技能脚本的公开API读取另行验证，没有付费模型请求；未启用包仅完成兼容性判断，不声称全部脚本经过安全或效果审查。

## DEV-088：开发进程重启后仍被容器中的旧配置覆盖

开发模式原本继承生产env_file。Compose在创建容器时保存环境快照，而进程环境又优先于文件，因此修改.env、重启Python后仍可能使用旧参数。问题在配置来源及优先级，不在热更新有没有监听到Python源码。

## DEV-083：暂停、修改要求与完成回调必须共同决定后续执行
