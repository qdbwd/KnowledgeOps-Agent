# 0026：按功能整理后端与前端源码

日期：2026-10-14。状态：按用户明确授权实施。

后端原有 80 个 Python 文件集中在包顶层，前端 35 个文件也基本平铺。文件名提供了线索，但同一能力的配置、执行与校验分散；原 `runtime.py` 同时承担图装配、状态、模型适配、控制中间件和业务工具，`api.py` 汇集了大量路由。这使阅读和修改都需要在一个很大的平面目录中查找。

用户确认借鉴 DeerFlow 整理后端并同时调整前端。这轮用短执行清单完成，不新建长期目标：核对引用及资源位置；保存公开合同作为对照；迁移并拆开主要职责；同步导入、说明和测试；用离线回归验证。

## 采用的组织方式

参照 [DeerFlow cb90f5dca47f68fec329746a53df7b437a11c4e8 的后端](https://github.com/bytedance/deer-flow/tree/cb90f5dca47f68fec329746a53df7b437a11c4e8/backend)，采用应用接入与 Harness 分区，以及 Harness 内模型、上下文、工具、权限、技能、MCP、子 Agent、本地执行按能力分包的方式。上游已进一步分发独立 Harness 包；本项目规模和依赖关系尚不需要照搬这个发布层级，继续维护一个 Python 包。

应用装配、HTTP 路由和后台调度归入 `app/`；知识、学习、长期记忆和材料各自成包；检索基础、持久化和部署配置单独归类。原 Runtime 的状态、模型适配、运行控制、领域工具分别提取，装配文件保留真实工具注册及中间件顺序。原 API 输入校验集中在 `app/schemas.py`，路由按功能拆分，应用工厂保留生命周期、来源校验和异常转换。既有学习与审批路由直接迁移。

前端采用 `app / features / shared / styles`，测试跟随功能；保留 Vite 入口和独立浏览器测试目录。参考分区原则，不复制上游 Next.js 应用目录或组件代码。

## 保持的合同与依赖边界

- `knowledgeops_agent.api:app`、`python -m knowledgeops_agent.worker` 和 `uv run scripts/dev.py` 保持可用。旧顶层 API/worker 只保留薄入口，内部代码和测试直接导入新实现。
- API 路径/Schema、模型可见的工具名称/Schema、提示正文、图节点与状态字段、数据库结构和快照逻辑资源标识保持原合同。根 Skills、配置、许可证和 vendor 不搬动。
- 新增集中式包资源定位，修正源码移动后原 `__file__` 相邻路径失效的问题；源码与 wheel 都读取同一份分发资源。
- 不为每个旧模块保留一个空转发文件。仓库内静态导入、延迟导入、动态导入和测试 patch 路径同步迁移；历史计划和证据不作为可执行入口。
- 不把目录名误当作依赖已经彻底解耦。Harness 仍组合本应用的服务，领域服务、数据库模型中的大文件这轮也没有全部再拆。早期 M0 图合同移到 `legacy/`，应用不加载，仅保留原有回归依据。
