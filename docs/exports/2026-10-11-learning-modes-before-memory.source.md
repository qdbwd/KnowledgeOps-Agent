# KnowledgeOps Agent：两种学习模式与学习配置增量实施计划

## 一、目标与产品行为

在现有应用上增加“交互学习”和“委托整理”两种模式，复用已有 Agent、工具、子 Agent、会话、队列、检查点和知识发布能力。

应用继续支持普通聊天和通用任务，不把所有用户请求都转换为知识整理任务。本次也不重做现有消息插入、排队、检索、上下文压缩或沙盒机制。

### 1. 区分会话、学习任务和运行

| 对象 | 含义 | 与其他对象的关系 |
|---|---|---|
| 会话 | 用户看到的聊天窗口 | 可以先后承载多个学习任务及普通讨论 |
| 学习任务 | 一个持续推进的学习目标，如“学习关系数据库与 SQL” | 保存目标、框架、进展、资料、个性化配置和整理结果 |
| 单次运行 | Agent 一次具体的执行过程 | 可以推进学习任务，也可以回答普通问题 |

**默认建议一个会话围绕一个学习任务，但不强制绑定。**

- 用户可以在原窗口结束上一项、开始下一项，也可以切回旧任务。
- 同一会话同一时刻只自动推进一个主要学习任务。
- 普通追问、临时插话不会自动创建新学习任务。
- 开始新任务时建立独立的工作上下文；旧聊天仍可查看，旧资料按需引用，不直接继承上一任务的全部专属要求。
- 切回旧任务时恢复其进展、材料和配置，不重新开始。
- 首版不增加同一学习任务横跨多个会话并行推进的功能。

### 2. 两种模式

| 行为 | 交互学习 | 委托整理 |
|---|---|---|
| 开始阶段 | Agent 帮助明确目标、建立框架 | 先对齐目标和框架，再连续推进 |
| 主要反馈来源 | 真人的提问、补充与纠正 | 读者子 Agent 的追问，加上真人随时介入 |
| 推进方式 | Agent 主动引导，等待真人参与关键讨论 | 在约定范围内持续完成各知识单元 |
| 正式保存 | 沿用当前自然语言授权和 UI 操作 | 获得任务级授权后，审读通过一篇，保存一篇 |
| 完成含义 | 本次讨论或用户指定的整理完成 | 已批准范围内的产物完成，且未隐瞒遗留问题 |

对宽泛的新主题，默认先展示简洁的目标理解、范围和框架，请用户确认。用户已经给出明确框架，或者明确授权 Agent 自行安排并开始执行时，不重复索取相同授权。

框架可以调整；显著扩大学习范围、改变最终用途等事项需要真人决定。普通内容细化由 Agent 完成。

### 3. 保留现有消息投递选择

用户仍然可以：

- 让消息排队，等待当前运行结束；
- 主动选择“引导当前任务”，把消息插入正在执行的运行。

委托整理只增加后续衔接规则：

- 处理完普通追问后，继续原整理任务。
- 每次准备自动推进下一轮之前，先处理同会话已排队的真人消息。
- 明确暂停、切换任务、撤回授权或遇到必须由真人决定的问题时，停止自动推进。
- 排队消息不会提前改变当前运行，也不会追溯撤销已经完成的保存。

这次不重新设计消息投递 UI，不将全部用户消息强制变成即时插入。

## 二、持续整理与子 Agent 如何协作

### 1. 采用主 Agent、读者和审读者三种职责

**主 Agent**保留与真人交互、检索、解释、组织材料、修订文档和保存的职责。

**读者子 Agent**依据学习配置，从目标读者角度寻找理解障碍、遗漏、例子不足及前后不连贯之处，提出有价值的追问。

**审读子 Agent**独立阅读完整草稿，对照任务要求、知识库规则和必要来源，检查内容与表达，不把前面“讨论过了”当作正确性证明。

不额外增加一个只负责转发消息的管理模型。持续调度和业务状态由程序管理，内容判断和任务内的行动选择交给 Agent。

子 Agent 复用当前 Deep Agents 委派能力，采用隔离上下文，按角色提供材料与工具。Deep Agents 已提供这种按提示词、工具和上下文边界配置子 Agent 的机制，本项目不重新实现子 Agent 引擎。[Deep Agents 子 Agent 文档](https://docs.langchain.com/oss/python/deepagents/subagents)

### 2. 每个知识单元的推进方式

一个单元可以对应一篇文档，也可以是后续合并成文档的一组连贯内容，不强行按标题数量切碎知识。

基本过程为：

```text
已确认的任务框架与学习配置
          ↓
主 Agent 检索、解释并形成内容
          ↓
读者提出针对性追问
          ↓
主 Agent 回答、补充、修订
          ↓
形成完整草稿
          ↓
独立审读 → 必要修订与复核
          ↓
检查任务授权、草稿版本与审读结果
          ↓
保存正式知识，推进下一单元
```

具体查什么资料、怎样解释、是否补充例子，由 Agent 根据内容决定；程序控制必须遵守的边界。

默认每个单元最多进行两轮读者追问、两轮审读修订。这是防止空转的工程默认值，不代表次数用完就通过：

- 已解决理解问题，可以提前进入下一步。
- 仍存在关键事实错误、重要遗漏或证据不足，保留草稿与问题，不自动发布。
- 可以继续处理不依赖该问题的其他单元。
- 有遗留单元时，最终状态明确显示“部分完成”或“需要处理”，不宣称全部完成。

参考 DeerFlow 对“子任务执行结束”和“验收条件满足”的区分，并保留未解决事项，而不是简单依赖子 Agent 返回“完成”。[DeerFlow 子任务验收测试](https://github.com/bytedance/deer-flow/blob/38c55c67f6010079f6a1a37af998b2278618499c/backend/tests/test_subagent_acceptance_followup.py)

### 3. 发布必须对应实际审读的版本

当前通用文件编辑可以触发知识同步，因此不能只在提示词里要求“先审读再保存”。

新增统一发布检查：

- 审读记录绑定具体草稿修订、正文哈希和任务要求版本。
- 审读后继续修改正文，会使原审读结果失效。
- 审读结果必须来自实际运行的审读角色，主 Agent 不能自行填写一个“通过”替代。
- 审读者需要获得完整草稿；长文沿用现有产物保存和分页读取能力。
- 业务发布工具与通用文件同步共用检查，避免通过文件工具绕过审读。
- 任务授权限定在已确认范围内，不扩展为任意知识库修改权限。

正式发布仍复用现有版本、引用、基础版本冲突、幂等回执和 BM25 索引更新机制。未通过的内容保留为工作文件和草稿。

“完整读取”和“检查通过”只能证明程序与审读流程执行，不能保证任意模型判断正确；这一限制需要如实展示。

### 4. 持续执行、停止与恢复

新增持久化的学习任务协调层，在现有单次运行结束后，根据任务状态安排下一步。继续使用现有 PostgreSQL、Celery、Redis 和检查点，不新增服务。

- 自动推进必须产生真实的进展变化，不能通过反复创建空运行维持“工作中”。
- 自动运行记录为系统推进，不伪造真人消息。
- 一次任务内部的子 Agent、重试和修订仍消耗预算。
- 沿用现有单次运行预算；同一知识单元跨运行补做时另外累计该单元预算，不能通过新建运行清零。
- 默认单元预算沿用当前的 40 次模型请求、80 次工具调用、20 次搜索和 1,200 秒活跃时间；恢复不自动追加额度。
- 已确认框架限定可自动处理的范围，不恢复已废弃的全项目累计次数上限。
- 关闭网页不取消后台任务；服务异常重启后沿用当前“等待用户手动恢复”的规则。
- 暂停保留进展；取消停止后续推进，并明确已经保存的内容仍然存在。

借鉴 DeerFlow 将交互方式落实到提示词与执行行为的一致策略，但本项目的委托整理仍允许真人介入，不直接套用完全无人值守模式。[DeerFlow 运行交互策略](https://github.com/bytedance/deer-flow/blob/38c55c67f6010079f6a1a37af998b2278618499c/backend/docs/RUN_INTERACTION_POLICY.md)

## 三、学习配置、数据与应用接口

### 1. 持久保存两层学习配置

**通用学习配置**描述跨任务适用的讲解与追问习惯，例如解释顺序、例子偏好、详略要求。

**任务个性化配置**描述本任务的用途、范围、自述基础、重点和表达要求，随任务长期保存。

读者子 Agent 的有效配置由两层组合；主 Agent 也读取这些要求，使讲解与追问保持一致。具体任务要求在本任务内覆盖通用默认值，临时用户指令不自动成为长期偏好。

此外，任务进展、当前材料与未解决问题作为运行上下文单独提供，不把它们全部混入角色文档。

### 2. 编辑、导入和版本管理

两层配置均支持：

- 查看完整 Markdown 内容。
- 通过聊天要求修改，或在界面直接编辑。
- 导入 Markdown、`SKILL.md` 风格的角色与学习方法文档。
- 查看修改差异、依据与历史版本。
- 导出、停用及恢复旧版本。
- 在新任务中明确选择复用旧任务配置。

导入先展示将应用的内容和范围，确认后生效。首版导入的是说明文档，不执行附带脚本，也不因为文档声明而启用工具、MCP 或文件权限。

配置正文使用现有文件存储保存不可变版本，PostgreSQL 保存身份、当前版本、来源与关联。聊天修改、UI 编辑和导入共用一个版本服务，不形成两套可独立修改的配置。

现有普通偏好继续保留；学习相关提取接入统一的学习配置更新路径。既有偏好不批量删除或未经审阅重写，装配时处理重复与冲突，避免同一要求被反复注入。

### 3. 根据真实反馈自动更新

延续已确定的“自动学习、可回退”方式：

- 明确的长期偏好可以更新通用配置。
- 本次任务的明确要求更新任务配置。
- 多次一致的真实反馈可以形成自动应用的偏好更新。
- 临时要求只影响当前任务或运行。
- 有冲突、证据不足或明显扩大适用范围的推断，保留为待确认建议。

每次更新保留真实消息来源、适用范围、修改原因和版本差异。用户手工编写或导入的要求不能被模糊推断静默覆盖。

**读者子 Agent 的追问、审读意见和模拟满意度，不作为真人反馈。**完成文档也不表示用户已经掌握知识。

每轮运行保存使用的配置版本。自动学习得到的新配置在下一轮采用；用户立即提出的纠正仍通过现有引导机制影响当前运行。恢复时保留原运行依据，显式变更另有记录。

### 4. 保存的数据与主要接口变化

新增以下业务数据：

- 学习任务：目标、范围、模式、框架、当前状态及授权依据。
- 知识单元：依赖、进展、材料、草稿、结果及未解决问题。
- 配置及修订：通用配置、任务配置、反馈依据与应用状态。
- 协作记录：读者问题、主 Agent 处理结果、审读结果及对应版本。
- 任务与运行关联：区分真人触发、自动推进和子任务。

现有运行、消息和知识文档增加可选的学习任务关联，旧数据保持有效。任务接续快照与会话展示分开：切换任务不清空聊天，也不误用另一任务的工作记忆。

后端增加学习任务管理、配置版本管理和协作结果查询接口。聊天控制和 UI 操作调用同一业务服务，继续核验真人授权、版本及重复请求。

前端增加：

- 当前学习任务及模式显示。
- 框架、当前单元、成果和待处理问题。
- 开始下一项、切回旧任务、切换模式、暂停和继续。
- 通用配置与任务配置的查看、编辑、导入和回退。
- 可展开的读者追问与审读详情。

主界面优先展示内容和进展，不把开发验收报告、调试事件或历史模型累计次数重新放进产品。

## 四、按依赖顺序实施与验证

| 步骤 | 具体产物 | 完成条件 |
|---|---|---|
| 1. 建立学习任务与作用域 | 数据迁移、任务与运行关联、单元进展、任务级接续 | 同会话可串行切换两项任务；配置和工作上下文不串用；普通聊天保持兼容 |
| 2. 实现两层配置 | 默认配置、文档版本服务、聊天/UI 编辑、导入导出及回退 | 重启后配置保留；任务结束后仍可复用；版本冲突明确反馈 |
| 3. 接入真实反馈更新 | 复用偏好提取入口，增加任务作用域、证据及更新规则 | 真人反馈可正确更新；临时指令、模拟读者意见和授权文字不被误存为长期习惯 |
| 4. 打通交互学习 | 学习任务提示装配、相关 Skills、框架引导及任务切换 | 新主题得到合适引导；具体追问直接回答；用户可改变方向；保存沿用真实授权 |
| 5. 打通一个委托单元 | 读者与审读角色、材料交接、追问修订及发布检查 | 一个完整单元可经过讨论、审读并保存；旧审读和伪造通过无法发布 |
| 6. 扩展为持续整理 | 自动推进、消息优先处理、预算、暂停恢复、独立单元继续 | 两个以上单元连续完成；排队和即时引导都生效；中断后不重复发布 |
| 7. 完成应用交互与交付 | 任务视图、配置编辑、协作详情、兼容验证和开发说明 | 用户能从聊天完成完整闭环，并能理解进展、失败原因和配置变化 |

实现时先完成最小闭环，再扩大覆盖；不先搭一套独立的大型工作流平台。

### 必须覆盖的验证场景

确定性测试重点覆盖：

- 同会话切换任务后，旧配置、旧授权和旧材料不会错误套用。
- 排队消息不进入当前运行；用户选择引导后只应用一次。
- 真人消息排队时，自动推进不能持续抢占。
- 用户暂停、取消或撤回授权后，不再自动发起下一轮或发布。
- 配置导入、版本冲突、回退、重复反馈及真人来源校验。
- 子 Agent 只能读取授权材料，不能写知识、授予权限或递归委派。
- 审读后正文改变、修订号过期、存在关键未解决问题时禁止自动发布。
- 通用文件同步与业务工具遵守同一发布检查。
- 重复队列通知、重启和恢复不重复计费或重复保存。
- 单元受阻时，独立内容可以继续，最终不能误报全部完成。

真实模型验证放在工程机制通过之后，仅覆盖新增闭环：一次交互学习，以及一个含两个知识单元的委托任务，包含真人纠正和实际审读修订。先估算调用量，不重跑无关旧效果实验，不启用默认关闭的 `call_model` 工具。

工程检查、真实运行轨迹与内容审读分别报告。模型没有按要求执行时保留失败证据，不靠重复调用获得一次偶然通过。

## 五、交付要求与后续长期目标

实施对象始终是 `D:\codes\KnowledgeOps Agent`。参考个人知识库任务的协作方式，但不把桌面个人知识库挂载、导入或作为应用运行数据。

继续使用当前模型、独立容器组及锁定依赖。Deep Agents 主要复用现成委派和工具机制；DeerFlow 主要借鉴交互策略、角色提示和验收边界。学习任务持续推进、真实反馈更新和知识发布衔接属于本项目的业务实现，不宣称上游已经提供完整成品。

实施前再次核对所用上游接口与当前依赖的兼容性；只有存在明确缺口且验证必要时才调整依赖，不为追最新版本盲目升级。

后续交给 Codex 的长期目标为：

> 在现有 KnowledgeOps Agent 中完成上述交互学习、委托整理和两层持久化学习配置。用户能够确认框架后持续整理、随时通过原有消息方式介入，并获得经实际审读后保存的知识文档；任务与配置可恢复、可解释、可回退。保留普通聊天、通用工具和现有权限边界，完成受影响工程检查、最小真实业务闭环及自然语言开发交付说明。

以下事项必须留给真人决定：显著扩大任务范围、扩大工具或数据权限、无法自行解决的外部阻塞，以及需要超出已明确范围的费用安排。普通实现问题、兼容性修复和计划内细节由 Codex 自主处理并记录。

最终同步现有架构说明、实施计划、项目上下文和进展记录，不新增相互竞争的计划。开发说明要沿实际运行过程讲清新增了什么、为什么这样设计、复用了哪些能力、数据如何流转及仍有什么限制。

**本阶段仅完成规划；不修改文件、不调用收费模型、不启动长期目标。**
