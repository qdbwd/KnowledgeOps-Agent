## 1. 目标与基本原则

本知识库是一套由用户兴趣和实际需求逐步形成的个人知识资料。

它将深入讨论与实践中形成的理解保存为可独立阅读的文档，减少对聊天记录的依赖，方便日后查找、回顾和运用。

**知识正文是核心。讨论和实践是两种知识形成方式；领域目录和任务视图是两种阅读入口。它们服务于同一套知识。**

目录、分类、链接、图示、任务视图和维护工具都服务于内容，不反过来要求内容填满某个预设框架。知识范围不限于求职、单个项目或计算机领域。现有分类是组织起点，不是必须覆盖的课程清单，也不是永久边界。

本库追求清晰、可靠和实用，不追求知识完全无重复、分类绝对唯一或关系图穷尽所有联系。

## 2. 知识形成方式与阅读入口

知识可以通过两种方式形成：

- **主题讨论**：从希望理解的概念、机制或领域出发，通过解释、追问和核验逐步形成认识。
- **任务实践**：从具体目标出发，将知识用于行动，在实施、观察和验证中加深理解，发现不足或形成新经验。

两者最终服务于同一套知识正文，不分别建设“理论知识库”和“实践知识库”。知识正文既可以保存原理，也可以保存方法、操作经验和排障知识。任务材料也可以充分解释理论，而不是只记录步骤。

对应的阅读入口有两种：

- **领域目录**：按知识主题寻找和阅读文章。
- **任务视图**：按某项实践目标寻找相关知识，理解它们怎样组织和运用，帮助以后复现。

同一篇正文可以同时被领域目录和多个任务视图引用。

**用户决定知识固化的时机与范围；维护代理负责内容质量与组织判断。** 知识形成方式不同，不改变这一授权边界。实践结束或出现阶段性成果，不自动触发知识入库；用户也可以在任务尚未结束时指定固化其中已经讲清的部分。

## 3. 文档角色

### 3.1 知识正文

围绕明确主题展开、可以独立阅读的知识文档。重点在于讲清原理、机制、方法、关系和边界。

正文按知识逻辑组织，不按聊天时间顺序组织。读者不需要先阅读原始对话才能理解文章。“知识本体”只是本库对这些通用正文的集合称呼，不意味着需要建立复杂的形式化本体系统。

不再设置独立的“问题专题”类型。问题可以成为讨论起点、文章切入点或阅读提示，但不能仅凭它来自提问就决定文档归属。例如，“为什么并发更新会丢失数据”可以形成通用知识正文；某项目一次数据丢失事故的排查过程则更适合放在该任务材料中。

### 3.2 参考资料

主要用于跳查的资料，例如命令速查、参数说明、规范清单和术语对照。参考资料仍需交代必要含义、使用条件和来源，不能只有脱离上下文的命令、数值或链接。

### 3.3 任务视图与任务材料

任务视图保存某个具体目标下的知识组织方式，包括相关知识、应用顺序和材料入口。这里的“任务”指具有具体目标和情境的活动，不把“长期学习知识”这一整体目的当作所有正文都应放入任务目录的理由。

任务材料保存完成该目标所需的具体分析、方法、步骤、选择依据、环境约束和验证结果，方便再次实施或回顾。二者可以在同一任务目录中配合使用，不要求每个小任务都拆成多份文件。

任务材料允许包含充分的知识解释。提炼完成后，这些解释可以保留，不必缩减成只能靠跳转才能读懂的步骤表。

### 3.4 导航文档

总入口和领域 README 帮助找到内容、理解局部组织与阅读顺序，不维护另一套重复正文。导航只反映实际存在的内容，不把待讨论主题或空提纲展示为已经完成的知识成果。

## 4. 文档边界与增量更新

文档边界由解释连贯性、主题独立性和查找便利性共同决定。不要求一个术语一个文件，也不要求一个学科只有一个大文件。一次讨论可以完善多篇文章，多次讨论也可以逐步形成同一篇文章。

整理新增知识时，根据实际内容判断：

- 是否属于已有文章的必要补充；
- 是否修正了旧解释或增加了适用条件；
- 是否形成了适合独立阅读的新主题；
- 合并后是否偏离原文主线；
- 拆分后是否造成大量重复或不必要的跳转。

这些是判断方向，不是机械分类算法。维护代理需要实际阅读相关正文作出判断，不能仅按标题、术语或预设分类表决定。

正文允许保留必要的概念回顾、例子和不同角度的解释。避免的是多份几乎相同的完整文章各自演变，而不是消除所有重复。

同一主题的新讨论应整合进文章逻辑，不简单堆在末尾；与旧内容冲突时，按证据和条件处理，不默认最新说法正确。知识允许增量形成：已经讲清且适合独立保存的部分可以先整理，不必等整个领域学完；尚未解决的问题保持明确边界。

│     └─ 知识库设计与决策.md

### 5.1 文件夹与领域 README

文件夹承担粗粒度分类和浏览功能。每篇正文选择一个主要位置，跨领域联系通过必要解释与链接表达，不复制多份全文。

现有计算机领域分类可以参考相关学科体系，但不再要求每篇文章逐项登记多套分类。新增领域以实际内容和查找需求为依据。

领域 README 承接局部目录功能，组织已有文章，可以提供简短的范围说明和阅读建议。不要求先写一篇学科主干文章，才能保存具体正文。如果以后形成了有价值的领域总论，再作为知识文章保存，不为支撑目录而提前生成。

### 5.2 总入口

`00_入口/知识库入口.md` 提供全库导航，连接领域目录、参考资料与任务入口，必要时展示少量关键的跨领域联系。总入口不逐条重复维护所有文章中的关系，也不沿用旧库已经归档的节点清单。

### 5.3 文档关系与图示

目录回答“在哪里找”，文档关系回答“为什么一起看、接下来可以看什么”。关系以正文中带有解释的标准 Markdown 相对链接为主要表达方式，例如前置、进一步展开、方法对比和应用。文档还应提供清楚的返回导航。

不要求把所有潜在联系都登记为边，也不因缺少关联文档就立即生成新文章。必要的基础可以直接在当前正文中解释。仅用于返回目录的导航链接不等于知识前置或其他语义关系。

文档级知识图谱是这些文档关系的展示方式，不是额外的实体抽取系统，也不要求图数据库。图示用于帮助理解整体或局部关系，不作为另一套独立维护的关系事实。因此，取消旧设计中“所有关系必须集中登记在总入口关系表”的要求。

普通 Markdown 是内容载体；阅读器不决定内容组织，也不作为打开文档的强制依赖。是否增加自动图示或索引工具，根据实际需求另行决定，不假定这些能力已经存在。

## 6. 知识提炼记录

任务材料中的知识可以根据用户指令提炼为通用正文。提炼不是按学科机械剪切段落，而是结合上下文重新组织，使其适合独立理解和长期保存。

对确有提炼内容的材料，使用轻量记录。下表是字段示意，不是本库已有任务：

| 主题 | 状态 | 正文位置与范围说明 |
|---|---|---|
| 某项机制或经验 | 待提炼／部分提炼／已提炼／无需提炼 | 对应文章、章节，或未处理的原因 |

记录规则：

- 按具体主题记录，不只给整篇任务材料打一个勾。
- “已提炼”必须有实际正文位置，并明确覆盖范围；已有正文已经覆盖时，核对并关联即可，不要求新建。
- “部分提炼”说明尚未整理的部分；“无需提炼”说明它为何只属于本次任务。
- 尚未核实的内容，在范围说明中标明，不因需要完成状态而强行形成结论。
- 用户未要求整理时，不主动展开提炼工作，也不为普通聊天建立完整的待办清单。

提炼记录不表示用户掌握程度，也不表示任务完成或正文已全面验证。它也不要求为了记录状态而先把聊天保存为任务材料：用户可以直接要求将一段讨论整理为知识正文。

任务材料保存的是特定情境下的组织和运用。正文后续更新，不意味着所有历史任务记录必须跟着改写；但仍被作为当前操作指南使用的材料，应检查相关变化是否影响其可用性。

## 7. 文档信息与检查边界

文档保留必要的信息，帮助识别、查找和维护：

- `id`：稳定标识，改名时尽量保持。
- `title`：可读标题。
- `type`：用途，采用“知识正文、参考资料、导航、任务视图、任务材料”。
- `summary`：说明主题与适用阅读场景。
- `updated`：最近文档修改日期，不代表最近全面核验日期。

这些信息放在文件开头的 YAML frontmatter 中；规则文件不强制套用知识文章的元数据模板。旧模块编号、复杂衍生关系字段和固定领域枚举不自动继承。其他字段仅在有实际用途时增加。

资料引用要尽量贴近所支持的结论。讨论或任务材料是内容形成的素材来源，不自动成为结论正确性的依据；不编造不存在的会话链接或未实际核对的外部来源。

检查分为三个独立层面：

| 层面 | 能回答的问题 | 不能据此推断 |
|---|---|---|
| 结构检查 | 链接、锚点、必要信息、标识和导航是否正常 | 正文正确、深入、完整 |
| 正文审读 | 解释是否连贯充分，是否保留关键内容，是否适合独立阅读 | 所有外部事实已经核验 |
| 事实验证 | 指定结论是否有依据，示例在何种条件下成立 | 全篇乃至全库均无问题 |

检查工具应适配已确认的新设计，不以旧工具的限制反过来决定文章结构。不以文件系统修改时间推断内容何时修改或核验，不要求知识正文禁止链接任务材料。

## 8. 归档规则与重要替代记录

### 8.1 新旧知识库边界

旧知识库完整归档，新活动知识库只继承经过筛选的规则设计和目录骨架，不自动继承正文、任务材料或旧导航内容。

实施时，先复制并校验归档，再清理明确范围内的活动文档；保留目录不等于承诺恢复原有文章或继续旧任务。新的入口和领域 README 按重置后的实际内容建立，不恢复旧文章清单。归档默认不参与阅读导航和知识整理。

归档保存原文件和目录，并附可核验的文件清单。恢复时先核对目标范围与现有文件，不能用旧快照直接覆盖后来新增的知识。归档不会递归包含自身。

### 8.2 两份规则文件的职责

- `AGENTS.md`：保存维护代理当前应执行的要求。
- 本文：保存概念定义、组织设计、理由及少量重要替代记录。

原《学习档案与维护约定》不再作为第三份现行规则，其中仍有效的内容分别并入上述两份文件，原件随旧库归档。普通正文更新不新增设计决策。只有知识组织、维护方式或边界发生重要变化时，才修订相关设计。

发现两份文件冲突时，依据用户最新明确要求消除冲突；尚未确定的选择先讨论，不用固定的文档优先级掩盖不一致。

### 8.3 保留的重要替代记录

| 原有方式 | 新的选择 | 原因 |
|---|---|---|
| 预先铺开框架、批量生成知识 | 深入讨论后，按用户指定范围固化 | 内容成熟度不能由目录完整度替代 |
| 求职背景主导知识组织 | 正文按知识组织，求职作为具体任务 | 服务长期、个性化的知识需求 |
| 追求知识完全无重复 | 保留有助于理解的重复，避免全文副本 | 可读性优先于形式上的完全去重 |
| 按“问题专题”等标签机械归类 | 按文档用途与实际内容判断 | 提问方式不能决定知识归属 |
| 三份规则文档交叠维护 | 两份分别负责执行与设计 | 降低重复和过时规则造成的冲突 |
| 中央表登记所有文档关系 | 正文链接表达关系，目录与图示提供入口 | 减少重复登记与维护负担 |

“实践任务自动提炼”没有被采用：无论知识来自讨论还是实践，固化时机与范围均由用户决定。
