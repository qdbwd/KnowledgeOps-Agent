# 知识整理与维护

整理的产物是可独立阅读和复习的知识正文。不要把聊天记录直接拼接，也不要把充分讨论压成只有结论的清单。领域核心规则始终适用；这里提供执行方法，不赋予任何发布权限。

## 确定本次内容与已有归属

从用户明确指定的主题、讨论段落、材料和目标出发。需要整理聊天时，capture_conversation 形成实际可见讨论快照，再读相关原文；快照证明说过什么，不证明外部事实正确。

搜索相关已存在的知识文章并读取可能需要改动的完整固定版本，包括摘要、分类、标签和关系。判断补充、修订、新建或关联，并简短说明理由。不能只看标题就合并，也不要因存在一点重复就机械拆文。

已经解释清楚且适合独立保存的部分可以先整理。无法确定的问题明确保留，不为了完整性编造结论或阻止用户保存已有成果。整理完成不等于用户学完。

## 组织正文

先确定主题主线，再把知识按逻辑关系组织：必要背景、核心机制、重要推导、例子、误解辨析、取舍与边界。每个章节是否需要取决于材料，不套固定数量。

保留用户追问中澄清的关键条件、反例与不同说法的区别；保留有助理解的图示描述或适当重画的图。删除被纠正的错误、寒暄和重复说法；不能连同解释过程一起删掉。

标题清楚，开头说明范围。长文提供导航；短文保持自然连贯。知识引用放在相关论断旁边，原样使用读工具返回的完整 citation。最终聊天里的来源清单不能代替正文内引用。

更新旧正文时把新知识整合进合适章节，而非一律末尾追加。省略的元数据表示沿用，明确空值才清空；关系只连实际存在且有阅读价值的文章。不擅自改变与本次任务无关的内容。

## 草稿与修订

已启用文件工作区时，先 ls/glob/grep 定位 knowledge/documents 中的文件，再 read_file 阅读、edit_file 精确修改，write_file 新建。可以组合这些工具和 execute 脚本处理复杂编辑，不必为每种文字操作建立专用工具。程序会在写工具之后同步版本、引用和索引：published 表示正式保存，draft_ready 表示仍待确认，sync_failed 表示文件已修改但同步失败，必须修正原因再用 sync_knowledge_files 补同步，不能宣称已经入库。同一待确认文件的连续修改会修订已有草稿。人工外部编辑不会被后台默默发布，需要明确要求同步。

prepare_changes/publish_changes 仍适用于明确的多文档事务、元数据与关系操作；已有草稿可用 read_changeset 阅读当前修订，再用 revise_changeset 携带 expected_revision 修改。通用文件编辑和业务工具共用正式版本规则，不要对同一修改重复创建两份草稿。修改需保留基础版本，发生冲突时重新读取并核对，不通过直接写入 knowledge/versions 绕过它。

展示正文或有代表性的完整段落，让用户能判断内容；不要只报“已完成”或列 ID。用户要求细节时给出足以审阅的完整内容和实际差异。

合并、拆分、批量归档需要展示实际影响。主动建议标记为主动提议；没有相应许可不能发布。程序提供的当前授权与准确修订决定是否可保存，旧对话中的“直接保存”不是新任务的永久授权。

## 交付前检查

读取 evidence-check 技能，分别检查结构、正文连贯性和事实依据。检查关键数值、否定与因果，尤其不要把“没有提到”写成“明确禁止”。

整理讨论时，回到原始资料核对旧回答中的解释；保留用户关心的推导，删除或改正没有依据的绝对化说法。修订后回读全文，防止新增段落与未改的旧段落互相矛盾。“未知”的陈述要精确到缺少的字段，不能抹去材料已经给出的部分事实。

需要独立核对或集中整合较长材料时，可以 call_model(prompt, material_refs)。提示词应给出本次范围、需要保留的解释/例子、输出体例和不允许的扩展；传入固定原文，不只给主 Agent 自己的摘要。辅助正文仍须由主 Agent 审读、准备草稿并通过业务工具保存。

最终说明实际保存的是草稿还是已发布版本、对应位置、未处理的问题及验证范围。没有发布回执不能说“已入库”。
